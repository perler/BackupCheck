# BackupCheck

Backup monitoring for Macrium Reflect with [healthchecks.io](https://healthchecks.io) alerting.

Scans backup repositories for recent `.mrimg` files, reports per-machine health to healthchecks.io, and auto-configures check settings based on device type. Runs as a Windows Scheduled Task.

## Features

- Monitors multiple backup repositories (local or UNC network shares)
- Auto-detects Macrium Reflect repositories via Site Manager
- Auto-provisions healthchecks.io checks on first ping
- Auto-configures check period/grace based on device naming convention
- Self-updating from GitHub releases
- HC API caching to minimize Management API calls
- Structured logging with 7-day rotation
- Meta-monitoring (monitors the monitor itself)
- Skips machines with active backups in progress
- Detects corrupted backup files (`.error_loading`) and deletes leftover ones automatically
- Runs a Macrium verify of an image set after its leftover error files are cleaned up

## Quick Start

### 1. Set up healthchecks.io

1. Create a project at [healthchecks.io](https://healthchecks.io)
2. Get your **Ping Key** and **API Key** from Project Settings > API Access
3. Configure alerting integrations (email, Slack, etc.)

### 2. Install

Download the latest release and run the installer as Administrator:

```powershell
.\Install-BackupMonitor.ps1
```

The installer prompts for:
- **Company ID**: Short prefix for check names (e.g., `ACME` creates checks like `acme-wks001`)
- **Ping Key / API Key**: From healthchecks.io
- **Repository credentials**: For NAS/share access
- **Task credentials**: Windows/AD account for the scheduled task

### 3. Verify

1. Check Task Scheduler for the `BackupMonitor` task
2. Run manually: `.\Monitor-Backups.ps1`
3. Check your healthchecks.io dashboard

## Configuration

### config.json

Generated by the installer:

| Setting | Description | Default |
|---|---|---|
| `configVersion` | Config format version | `2` |
| `companyId` | Prefix for check names | (set during install) |
| `repositories` | Backup repository paths | (auto-detected) |
| `airGapRepositories` | Roots of air-gap media (USB Copy targets), optional — see below | (none) |
| `backupMaxAgeHours` | Max backup age in hours | `24` |
| `backupFilePattern` | File pattern for backups | `*.mrimg` |
| `skipIfRunning` | Skip machines with active backups | `true` |
| `deleteErrorFiles` | Delete leftover `.error_loading` files once they're old enough | `true` |
| `errorFileMinAgeHours` | Minimum age (hours) before a `.error_loading` file is deleted | `24` |
| `verifyAfterErrorCleanup` | Run a Macrium verify of the image set after its error files are cleaned up | `true` |
| `mrverifyPath` | Full path to `mrverify.exe`, if not found via the registry or default install path | (auto-detected) |
| `verifyPassword` | Password for password-protected/encrypted image sets, used only for verify | (none) |
| `healthchecksBaseUrl` | Ping URL | `https://hc-ping.com` |
| `autoDetectRepositories` | Auto-detect repos on each run | `true` |
| `updateUrl` | Custom URL for update checks | (GitHub raw URL) |

### Error file cleanup (`deleteErrorFiles`)

Leftover `.error_loading` / `.error_loading1`, `.error_loading2`, ... files are left behind by an
interrupted Macrium backup and can safely be deleted. Enabled by default: once a file has sat for
at least `errorFileMinAgeHours` (default 24h) and no backup is currently running for that machine
(the existing `skipIfRunning` detection), the monitor deletes it and logs the full path and size. A
delete that fails (e.g. the task account has no delete right on the share) is logged as a warning
and the file is left in place, still counting as a corrupted file. Set `deleteErrorFiles` to `false`
to go back to detect-and-warn-only.

### Macrium verify after cleanup (`verifyAfterErrorCleanup`)

Enabled by default: once one or more leftover `.error_loading` files for a machine are deleted (see
above), the monitor runs [Macrium's own `mrverify.exe`](https://knowledgebase.macrium.com/display/KNOW/Verifying+image+and+backup+files+from+the+command+line)
against the image set they belonged to — an interrupted backup is exactly what that tool exists to
check. The image set is identified from the deleted file name(s) (`<ImageID>-NN-NN.mrimg`); if that
can't be parsed, the newest image set on disk for that machine is verified instead.

`mrverify.exe` can take hours to verify a large image set over SMB, and the monitor runs hourly, so
it is launched **detached** — a hidden PowerShell child waits for it and writes its exit code to a
result file next to the monitor's own state, while the monitor's run finishes normally. Only one
verify runs per machine at a time. Once a result appears on a later run:

- **Exit code 0**: logged as OK, "Macrium verify passed for image set &lt;ID&gt;" is added to the
  status message once, and the pending state is cleared.
- **Exit code 1**: the machine's check **fails** with "image set &lt;ID&gt; failed Macrium
  verification, see &lt;log&gt;" — and keeps failing on every run until a **newer** image set than
  the failed one appears, not just once.
- **No result and the process is gone** (killed, crashed, box rebooted): logged as a WARN and
  retried once; a second silent death gives up without failing the check.

`mrverify.exe` is located via, in order: the optional `mrverifyPath` config key, the Macrium Reflect
install location (read from the registry), then the default
`C:\Program Files\Macrium\Reflect\mrverify.exe`. It is a separate download from Macrium, not part of
the Reflect installer — if it isn't found anywhere, verification is skipped with a WARN ("verify
skipped: mrverify.exe not found") and everything else behaves exactly as without this feature.

Password-protected/encrypted image sets are supported via the optional `verifyPassword` config key.
That password is never written to a log line or to disk on the monitor's side — it reaches the
detached verify process only through a process environment variable, set immediately before launch
and cleared immediately after. It does still appear as an `mrverify.exe` command-line argument on
the box while it runs, which is inherent to `mrverify.exe`'s own command-line-only interface.

Set `verifyAfterErrorCleanup` to `false` to turn this off entirely.

### Air-gap media (`airGapRepositories`)

Optional. Each entry is the **root** of a removable medium that a NAS copy job (Synology USB Copy
or similar) mirrors the backup share onto, so machines sit one level down:
`<root>\<share-copy>\<MACHINE>\...\*.mrimg`. The monitor asserts, per machine, that the **newest
image chain is restorable**: a `-00-00` base exists **and** every member carries the Macrium
end-of-file marker in its last 64 bytes (a copy that died mid-write has no marker). Files that are
not named as chain members (`_Conflict` artefacts, `.tmp` fragments) are counted but never satisfy
the assertion — Macrium cannot see them either. A member without the marker written within the
last hour is reported as *in progress*, not failed.

The verdict goes to one check, `{companyId}-usb-copy`, with a line per machine in the ping body;
any failed machine fails the check. If no medium is reachable the check is **not pinged**, so it
goes late rather than reporting either way.

## How It Works

1. **Log rotation**: Cleans entries older than 7 days from `backupcheck.log`
2. **Self-update check**: Fetches `latest.json` from GitHub (once per 24h), downloads and applies updates if available
3. **Repository scanning**: For each repository, scans subdirectories (one per machine)
4. **Health check**: For each machine, checks for recent `.mrimg` files within the configured threshold
5. **HC ping**: Sends success/fail ping with version-tagged status message
6. **HC configuration**: Auto-configures check period, grace, and tags (cached to reduce API calls)
7. **Air-gap check**: Walks `airGapRepositories` (if configured) and pings `{companyId}-usb-copy`
8. **Meta-monitoring**: Pings a `{companyId}-monitor-health` check after each run — `/fail` when
   none of the configured repositories was reachable, so a dead NAS does not look healthy

### Check Naming

Pattern: `{companyId}-{machineName}` (lowercased)

Examples: `acme-wks001`, `acme-srv003`, `acme-nb002`

### Self-Update

The monitor checks GitHub for updates every 24 hours:
- Fetches `latest.json` from the repo
- Compares version strings
- Downloads release zip, verifies SHA256 checksums
- Backs up current files (`.bak`), extracts new ones
- Re-launches with `-SkipUpdateCheck` to avoid loops

If the update fails at any step, the current version continues running.

## Offline Machine Handling

For workstations and notebooks that are legitimately offline (weekends, holidays, travel), the companion script `pause-offline-checks.py` runs on the coordinator server and:

- Queries Atera RMM for agent online/offline status
- Mutes notification channels for offline machines (prevents false alerts)
- Restores channels when machines come back online

This will be replaced by the coordinator API in v2.1.

## Troubleshooting

### Checks not appearing
- Verify ping key in `.env`
- Run `Monitor-Backups.ps1` manually and check console + `backupcheck.log`
- Ensure TLS 1.2 connectivity to healthchecks.io

### Access denied to repositories
- Verify `REPO_USERNAME`/`REPO_PASSWORD` in `.env`
- Check the scheduled task user has network access

### False "down" alerts
- Adjust `backupMaxAgeHours` for your backup schedule
- Check device type settings match your check periods
- For offline machines, ensure `pause-offline-checks.py` is running

### Updates not applying
- Check `backupcheck.log` for update errors
- Verify internet access to GitHub from the server
- Delete `.last-update-check` to force an immediate check
